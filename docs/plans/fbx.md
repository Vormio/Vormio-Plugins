# FBX 插件设计计划

状态：**已确认，待实施**（2026-10-16 确认 X1 至 X12，以及名称中的 “FBX” 只用来说明用途）。路线图“下一批（2026-10-16 排定）”的第 3 项：2026-10-16 决定第四种格式是 FBX。首个版本 0.1.0 用 SDK 0.0.10（`apiVersion: 5`），在第 0 项（Core 0.0.10 的收尾）合并之后实施。上一版插件没有做过 FBX，没有可参考的实现。

## 1. 目标

FBX 是 Autodesk 的私有格式，DCC 软件（Maya、3ds Max、Blender）与游戏引擎之间交换带骨骼、蒙皮与动画的模型时最常用；美术的素材文件夹里 FBX 往往比 glTF 多。它与前三种格式都不同：

- 文件里的贴图路径大多是作者机器上的绝对路径（`C:\Projects\hero\textures\body.png`），宿主会归为外部；真正能读到的是同一目录中的同名文件，这是一个推断。
- 二进制 FBX 可以把贴图内嵌在文件里（`Video` 对象的 `Content`）。
- 对象之间的关系不是嵌套写出的，而是一张 ID 连接表（`Connections`）：节点连几何体与材质，材质按属性名连贴图，蒙皮连簇再连骨骼节点，动画曲线连到节点的属性。组成分析就是把这张表读成子资源与引用。

插件 ID `vormio-plugins.fbx`，目录 `plugins/fbx/`，显示名称“FBX 模型”。名称中的 “FBX” 是 Autodesk 的商标，只用来说明用途（与 [Spine 设计计划](spine.md) §10 问题 1 相同；2026-10-16 确认，不构成法律判断）。

```text
hero.fbx        节点层级、几何体、材质、贴图对象、蒙皮、动画；Connections 把它们连起来
   │  Video 对象写出 RelativeFilename 与 Filename（常是作者机器上的绝对路径），或内嵌 Content
   ▼
textures/body.png（写明的相对路径），或与 hero.fbx 同目录的 body.png（推断）
```

## 2. 决定（2026-10-16 确认）

| 编号 | 决定                                                                                                                                                                                                                                                                                                                                                                                         | 理由                                                                                                                                                                                     |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| X1   | 0.1.0 一次声明三个扩展点：`fbx` 的缩略图、查看器与分析器；`companionFormats: png, jpg, jpeg, tga, bmp`（与 OBJ 相同）                                                                                                                                                                                                                                                                        | 扩展点后加会改变权限指纹（O1）。TIFF 浏览器不能解码，DDS 与 PSD 是 FBXLoader 不支持的类型，声明了也显示不了，列入不支持的情况                                                            |
| X2   | 缩略图与查看器用 three.js 0.186.1 的 `FBXLoader`（随它一起的 fflate 解压、`NURBSCurve`、`TGALoader`）；分析器自写解析二进制节点树与 ASCII 文本，不加载 three.js，也不解压数组                                                                                                                                                                                                                | 与 glTF、OBJ 一致：渲染用成熟的读取器，分析只需要结构。组成只用对象、属性与连接，顶点等数组（二进制中按 zlib 压缩）可以跳过，分析器页面不需要 fflate                                     |
| X3   | 识别：二进制文件以 `Kaydara FBX Binary  \0` 开头；ASCII 文件开头的注释写着 “FBX x.y.z project file”，或第一个顶层节点是 `FBXHeaderExtension`。两者都不是的文件分析失败（“不是 FBX 文件”），缩略图与查看器同样失败，不回答“不适用”                                                                                                                                                            | `.fbx` 只有 FBX 使用，没有“不是我的格式”的情形                                                                                                                                           |
| X4   | 版本范围与 FBXLoader 相同：二进制 6.4（6400）起，ASCII 7.0（7000）起；7.5 起的二进制记录头是 64 位。更低的版本分析失败并说明原因；比 7.7（7700）新的照常分析并附警告                                                                                                                                                                                                                         | 读得出就画得出；更老的文件请用新版工具重新导出                                                                                                                                           |
| X5   | 子资源：节点（`Model`，按属性类型细分为网格节点、骨骼、空节点、相机、灯光等，层级按节点之间的连接，根是文档）、几何体（`Geometry`：网格、NURBS 曲线、形变目标 `Shape`）、材质、贴图（`Texture`）、图像（`Video`，内嵌的注“（内嵌）”）、蒙皮（`Deformer` 的 `Skin`）及其簇（上级为蒙皮）、形变（`BlendShape` 及其通道）、动画（`AnimationStack`，名称后注层数与曲线数）。名称是对象名去掉类名 | 与 FBXLoader 建出的场景对应得上；动画层、曲线节点与曲线数量大，只计数不列                                                                                                                |
| X6   | 内部引用按连接表：节点 → 几何体、材质（按顺序）；材质 → 贴图（属性名作角色：`DiffuseColor` 写“漫反射贴图”，`NormalMap` 写“法线贴图”等，其余照属性名）；贴图 → 图像；几何体 → 蒙皮与形变；蒙皮 → 簇（“簇”）；簇 → 骨骼节点（“绑定骨骼”）；动画 → 曲线连到的节点（“动画目标”，同一对象只报告一次）。连接指向不存在的 ID 时记警告略去                                                           | §4 的角色与 glTF、Spine 一致，使用者在三种格式间看到同样的词                                                                                                                             |
| X7   | 文件引用：图像的 `RelativeFilename`（没有时 `Filename`）原样作写明的引用，角色“图像文件”，证据是对象 ID 与字段名。写明的路径是绝对路径（盘符、UNC 或以 `/`、`\` 开头）时，另报告一条推断的引用：与 FBX 同一目录中、与写明路径同名（去掉目录）的文件，依据“与文件中写的贴图同名”。有内嵌内容的图像不报告文件引用                                                                              | FBXLoader 也优先用 `RelativeFilename`。绝对路径宿主归为外部，不算缺失；同目录的同名文件是真实约定，用 R2 的推断引用正好表达。写明的相对路径（含 `..`）不另推断，避免同一目标既写明又推断 |
| X8   | 查看器：旋转、缩放、取景（glTF 与 OBJ 的 `framing.ts`、`stage.ts` 再各复制一份，O6 的结论不变），FBXLoader 建出的材质与贴图，蒙皮与形变目标；动画播放照 glTF 0.3.0 的控件（片段下拉、播放/暂停、进度条，自动播放第一段，`prefers-reduced-motion` 时停在第一帧）；文件中的灯光去掉，只用舞台灯光；相机 0.1.0 不切换                                                                           | 与另外两个三维查看器看起来一样；FBX 常带角色动画，播放是看 FBX 的主要目的；文件灯光会让同一模型在三个查看器里颜色不同                                                                    |
| X9   | 贴图读取：查看器与缩略图先用插件自己的解析器读出图像对象的文件名，按 X7 的规则决定读哪个文件（相对路径按原样读；绝对路径改读同目录的同名文件），用 `readCompanion` 读成 blob 地址，再通过 `LoadingManager.setURLModifier` 交给 FBXLoader；读不到的贴图列为原因，材质只用颜色显示（同 glTF）。内嵌的贴图由 FBXLoader 自己解出                                                                 | FBXLoader 直接拿文件里的路径去取，绝对路径取不到；与 OBJ 改写材质库给 MTLLoader 的做法相同                                                                                               |
| X10  | 定位请求（路线图第 2 项）：第 2 项先完成时 0.1.0 一并实现节点、几何体与材质的定位，否则留到 0.2.0                                                                                                                                                                                                                                                                                            | 用同一套做法，不另设计                                                                                                                                                                   |
| X11  | 测试素材全部由 `scripts/fixtures/fbx.ts` 生成，ASCII 与二进制两种写法各一份同样的内容；二进制写法按公开描述（Blender 基金会 2013 年的二进制格式说明与 Blender 的 FBX 导出器的字段顺序），7.4（32 位记录头）与 7.5（64 位记录头）各一份。不使用外部模型，也不使用 three.js 示例中的 FBX                                                                                                       | AGENTS.md 的素材规则；three.js 示例里的 FBX 来源与许可不清楚。FBXLoader 能否读取生成的素材本身是测试的一部分                                                                             |
| X12  | 不使用 Autodesk FBX SDK；解析依据社区的格式描述与 three.js 读取器的读法，测试用 FBXLoader 读取同一文件核对（对象的名称与数量）                                                                                                                                                                                                                                                               | FBX 没有公开规范，SDK 的许可不适合打进 MIT 的插件包                                                                                                                                      |

## 3. 分析器

**解析**（`src/fbx-file.ts`，无 DOM，Node 测试直接用）：

- 二进制：文件头 27 字节（标识、版本），之后是节点记录：结束偏移、属性数、属性字节数（7.5 起各 64 位，之前 32 位）、名称、属性、子节点、13 或 25 字节的空记录结尾。属性类型 `Y`、`C`、`I`、`F`、`D`、`L`、`S`、`R` 与数组 `f`、`d`、`l`、`i`、`b`：数组只读长度与编码，内容跳过（不解压）；字符串中的 `\0\x01` 分隔对象名与类名。
- ASCII：按行的 `名称: 值, 值 {` 结构，值是数字、带引号的字符串或 `*N { a: … }` 数组（只读长度）；对象名写成 `Model::hero`。
- 只保留分析用的节点：`FBXHeaderExtension`（版本、创建工具）、`GlobalSettings`（上轴、单位）、`Objects` 下的各类对象及其 `Properties70`（贴图路径、类型等）、`Connections`。其余节点跳过。
- 上限：报告超过 10,000 个子资源或 4 MiB 时，按动画、簇、形变通道、贴图与图像、材质、几何体、节点的顺序从最后一个开始略去，报告标为部分完成（共用 `shared/report.ts` 的 `withinLimits`）。

**报告**：子资源与引用按 X5 至 X7；每份报告用 SDK 的 `parseReport` 校验。诊断：连接指向不存在的 ID（警告）、同一 ID 出现两次（警告）、无法识别的对象类型（信息，不列出）、截断或损坏的记录（分析失败并说明在哪个偏移）、比 7.7 新的版本（警告）、`UnitScaleFactor` 不是 1 时一条信息（查看器不按单位缩放，取景不受影响）。

## 4. 缩略图与查看器

- 缩略图：隐藏页面中用 WebGL 渲染初始姿态（第一段动画第 0 秒），按顶点取景，透明背景，宿主给出的最长边；贴图读不到时只用颜色，缩略图照常生成（O7）。
- 查看器：X8 与 X9。底部说明栏写“FBX 7.4 · 三角形数 · 节点数 · N 段动画”，读不到的贴图与 FBXLoader 的警告（不支持的贴图类型、多层动画只取第一层、正交相机）列在说明里。
- 就绪之前不依赖动画帧（G4）；页面隐藏时停止绘制循环（G6）；每帧时间增量上限 0.1 秒。
- 上轴：FBXLoader 会把 Z 向上的文件转正，不另处理；单位不缩放（FBXLoader 只记在 `userData`），取景按实际尺寸。

## 5. 测试素材

`scripts/fixtures/fbx.ts` 生成 `fixtures/fbx/`（每份都有 ASCII 与二进制两种写法，二进制 7.4 与 7.5 各一份）：

- `basic/`：一个带两个材质与一张 PNG 贴图（相对路径 `textures/crate.png`）的立方体；一个两根骨骼、一段动画的蒙皮模型，带一个形变目标。
- `layout/`：贴图写成绝对路径（`C:\art\hero\body.png`），同目录放 `body.png`（推断引用能解析）；另一份同目录没有同名文件（推断未找到）。
- `embedded/`：内嵌 PNG 的二进制 FBX（ASCII 的内嵌是 base64，也生成一份）。
- `problems/`：缺失的相对路径贴图、指向不存在 ID 的连接、截断在对象中间、6.1 版本的二进制与 ASCII 文件头、普通文本改名为 `.fbx`、DDS 贴图路径。
- 真实导出（Maya、Blender、Mixamo 等）只在手工验收时临时放进关联文件夹，不入库。

| 场景                                                                                                                                 | 现状                                                                                                               | 可能的需求                                                                                          |
| ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |

## 7. 不在范围内

- FBX 6.x 的 ASCII 文件与 6.4 之前的二进制文件；FBX SDK 独有的功能（约束、自定义属性的语义、场景参考）。
- 正交相机、文件中的灯光与环境、多层动画（FBXLoader 只取第一层）、分层贴图（只取第一层）、NURBS 曲面（FBXLoader 只支持 NURBS 曲线）、单位缩放。
- DDS、PSD 与 TIFF 贴图：宿主不读或浏览器不能解码；分析器照常报告引用。
- `.fbm` 文件夹与工程 `textures/` 文件夹的约定（§6）。
- 写出或修改 FBX。

## 8. 测试与验收

- **Node 测试**：解析器读二进制 7.4、7.5 与 ASCII 的素材，三种写法得到同一份报告（证据除外）；各类子资源、连接与角色；文件引用与推断引用（X7 的四种路径写法：相对、`..`、盘符、UNC）；内嵌图像；诊断与截断；上限；`parseReport`。
- **Chromium 测试**（替身宿主）：缩略图与查看器在有贴图、绝对路径贴图、内嵌贴图、缺贴图时的画面；动画播放、暂停与拖动；6.1 与非 FBX 文件的失败原因；就绪不依赖动画帧；FBXLoader 读到的节点、材质与几何体名称与分析器报告相同（X12）。
- **测量**：生成一个约 100 MB 的 FBX（在测试中生成，不入库；大量顶点与一张大的内嵌贴图），记录分析、缩略图与查看器的耗时，决定是否在 README 写明大小上限。
- **手工验收**（Core 0.0.10）：启用确认框列出的权限；网格中的缩略图；查看器播放动画、切换片段；`.fbx` 的组成、引用与被引用，绝对路径的贴图显示为外部、同目录同名文件作为推断引用已解析；删除贴图后写明的引用显示缺失、推断的显示未找到；至少一份 Maya 或 Blender 导出与一份 Mixamo 角色的真实文件（临时放入，不入库）；原文件不变。记录 Core 版本与未覆盖的部分。

## 9. 实施顺序

1. 素材脚本：ASCII 写法与二进制写法（7.4、7.5），先用 FBXLoader 在 Chromium 中确认能读。
2. 解析器与分析器（Node 测试）。
3. 缩略图与查看器（Chromium 测试），动画控件照 glTF。
4. 插件 README（格式与版本、能力、不支持的情况、依赖与许可：three.js MIT，含 FBXLoader、fflate 与 NURBSCurve）；路线图插件表加 FBX 0.1.0；`release.json` 在手工验收通过后再加入。
5. 手工验收；真实导出中遇到的贴图位置约定决定 §6 是否提 issue。
