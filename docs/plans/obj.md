# OBJ 插件设计计划

状态：**0.1.0 已实现**（2026-10-15，路线图“下一批”第 3 项），结论写进了[插件 README](../../plugins/obj/README.md)，待手工验收；§7 中多个材质库的场景在 #3 提出后，Core 另立为 Vormio/Vormio-Core#9。0.1.0 用 SDK 0.0.7（`apiVersion: 3`）。**0.2.0**（2026-10-15）：Core 0.0.9 解决了 R3，只有一个材质库时 `usemtl` 的材质连到 `.mtl` 中的材质（§7），SDK 0.0.9（`apiVersion: 4`），已在 Core 0.0.9 上手工验收（§9）。**0.3.0**（2026-10-15，试用中）：Core 0.0.10 承接 Vormio/Vormio-Core#9，多个材质库时每个材质把全部材质库列为候选（`uris`，后写的优先），SDK 预发布版 0.0.10-rc.1（`apiVersion: 5`），见 §11。

实施时与草案的不同：

- O6 没有共用：`three` 只是 glTF 与 OBJ 插件自己的依赖，`shared/` 中的代码解析不到它（根目录的 `node_modules` 没有 three，加成根目录的开发依赖又违反“插件代码的依赖写在插件里”）。取景与灯光（`framing.ts`、`stage.ts`）在 OBJ 插件中各保留一份副本，文件开头写明要与 glTF 保持一致。不依赖 three 的“配套文件读取失败的原因”移到了 `shared/companions.ts`，glTF 随之改用，行为不变。
- 注释只认整行的 `#`，与 three.js 的 OBJLoader、MTLLoader 相同；行中的 `#` 是文件名的一部分（素材 `layout/` 的贴图名就带 `#`）。
- MTLLoader 只认识 `-bm`、`-s`、`-o`，并把其他选项当作文件名，所以查看器把贴图语句改写成只带这三个选项、文件名已编码的形式再交给它（`mtlForLoader`）。
- 贴图读不到时 three.js 会把材质画成黑色，插件去掉这张贴图，材质保留自己的颜色（O7 的补充）。
- §8 中“点与线元素不显示”不成立：OBJLoader 会画出线与点，查看器照常显示，分析器不为它们记诊断。
- 判断“不是 OBJ”除了 NUL 字节，还要求整个文件没有任何 OBJ 语句；只有注释的文本也算不是 OBJ。
- 测量（§9）：114 MB、196 万个顶点与 196 万个四边形的 OBJ，在开发机的 Chromium 中分析 1.7 秒、缩略图 5.9 秒、查看器 5.0 秒就绪，都在宿主时限之内；垃圾回收之后的 JS 堆很小，解析过程中占用较多。README 写明这些数字，不设大小上限。

## 1. 目标

OBJ 是第三种格式，选它的理由（2026-10-15 决定）：

- 它的引用链与 glTF、Spine 都不同：`.obj` 用 `mtllib` 写出材质库文件名，`.mtl` 再用 `map_Kd` 等写出贴图文件名。分析器要处理两种文件，每种都有自己的文件引用。
- `usemtl` 按名称使用另一个文件（`.mtl`）中的材质，是 R3（Vormio/Vormio-Core#3）在 Spine 之外的第二个真实使用方。
- three.js 的 `OBJLoader` 与 `MTLLoader` 已随 glTF 插件的依赖存在（three 0.186.1，MIT），不引入新的许可。

插件 ID `vormio-plugins.obj`，目录 `plugins/obj/`，首个版本 0.1.0，显示名称“OBJ 模型”。

```text
chair.obj      顶点、面、对象与组；mtllib chair.mtl；usemtl wood
   │  mtllib 写出文件名（可以有多个，相对 .obj）
   ▼
chair.mtl      newmtl wood；map_Kd textures/wood.png；bump …
   │  贴图语句写出文件名（相对 .mtl）
   ▼
textures/wood.png
```

## 3. OBJ 分析器

**子资源**：

| 类别 | key                | 名称                                  | 上级     |
| ---- | ------------------ | ------------------------------------- | -------- |
| 对象 | `objects/<序号>`   | `o` 的名称                            | —        |
| 组   | `groups/<序号>`    | `g` 的名称（多个名称用空格连接）      | 所在对象 |
| 材质 | `materials/<序号>` | `usemtl` 用到的材质名，按首次出现排序 | —        |

名称附带面数，例如“seat（120 个面）”。没有 `o` 与 `g` 的文件只有一个隐含的对象“默认”。

**文件引用**：每条 `mtllib` 的每个文件名引用材质库，角色“材质库”，证据“第 N 行”。`mtllib` 后的文件名以空格分隔，含空格的文件名在规范上无法表示：按空格切开，并在一行有多个文件名时记一条信息诊断，说明这样的切法（`OBJLoader` 只用最后一个材质库，见 §5）。

**内部引用**：组 → 它使用的材质（角色“使用材质”）。

**诊断**：面引用了不存在的顶点（越界或零）：警告；不认识的语句：信息，同一种只报一次；`usemtl` 出现但没有任何 `mtllib`：信息。

**上限**：与 SDK 的 `reportLimits` 一致；超出时先保留文件引用与材质，再按对象、组的顺序略去，报告标为部分完成。

**读取**：大文件按块读取并逐行解析，不一次解码整个文件；只统计面数，不构建几何体。

## 4. MTL 分析器

**子资源**：每个 `newmtl` 一个材质（`materials/<序号>`，名称是材质名）。

**文件引用**：材质的贴图语句（`map_Ka`、`map_Kd`、`map_Ks`、`map_Ke`、`map_Ns`、`map_d`、`map_bump`、`bump`、`norm`、`disp`、`decal`、`refl`）引用贴图，角色用中文名（例如“漫反射贴图”），证据“第 N 行”。语句的选项（`-s`、`-o`、`-bm`、`-clamp` 等）按规范的参数个数跳过，余下部分是文件名，可以含空格。`refl -type cube_*` 的六个面各是一条引用。

**诊断**：重复的材质名：警告（`MTLLoader` 用后一个）；贴图语句之前没有 `newmtl`：警告；不认识的语句：信息。

## 5. 缩略图与查看器

- `OBJLoader.parse` 读取主文件；它只记录最后一个 `mtllib`，所以插件先用自己的解析取出全部 `mtllib`，按顺序用 `MTLLoader` 读取并合并成一份材质表，后面的同名材质覆盖前面的（与多数工具一致；README 写明）。
- 配套读取像 glTF 一样按 `input.url` 的相对地址进行，失败的原因用 `readCompanion()` 查明。
- 查看器沿用 glTF 查看器的操作：旋转、缩放、平移，`F` 取景、`R` 复位；底部信息“N 个三角形 · M 个材质”。
- 缩略图：默认方向取景，与 glTF 相同的灯光与环境。
- 很大的 OBJ（数百 MB 的扫描模型）：`OBJLoader` 在主线程同步解析，可能超出宿主时限（缩略图 30 秒，查看器 15 秒就绪）。0.1.0 不做分块或 Worker 解析，超时照常显示，README 写明；测量见 §9。

## 6. 测试素材

`scripts/fixtures/obj.ts` 生成 `fixtures/obj/`，贴图复用 `scripts/fixtures/png.ts`：

- `basic/`：一个带两个对象、三个组、两个材质与贴图的模型；材质库在同目录，贴图在 `textures/`，文件名带空格。
- `layout/`：两条 `mtllib`、材质库在 `../materials/`、贴图语句带选项。
- `no-material/`：只有几何体，没有 `mtllib`；带顶点颜色、没有法线。
- `problems/`：缺失的材质库、缺失的贴图、`usemtl` 找不到的材质、越界的面索引、截断的文件、TGA 贴图。
- `not-obj/`：模拟编译器目标文件（COFF 与 ELF 的文件头加若干字节）与一个普通文本文件，验证“不适用”。

## 7. 等 Core 的部分

| 需求                                                      | Core issue           | 状态                                              | 补齐之前插件的做法                                                                                         |
| --------------------------------------------------------- | -------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| R3：`usemtl` 引用指向 `.mtl` 报告中的材质（跨文件子资源） | Vormio/Vormio-Core#3 | Core 0.0.9 已解决，SDK 0.0.9                      | （已解决）0.2.0 起只有一个材质库时连到材质，见下                                                           |
| 多个材质库时，引用的目标在几个文件之一中                  | Vormio/Vormio-Core#9 | Core 0.0.10 承接，SDK 预发布版 0.0.10-rc.1 试用中 | 0.3.0 起用 `uris` 列出全部材质库作候选（§11）；0.2.0 多个材质库时不报告 `uriKey`，只报告材质名与各个材质库 |

R3 试用时，`.mtl` 分析器的材质 key 改为基于材质名（与 Spine 图集区域按名称的 key 相同的规则），OBJ 分析器的材质引用带 `uriKey`。`usemtl` 可能在多个材质库中查找，所以目标文件只能是推断的：这个场景（一个引用的目标在多个文件之一中）在 #3 提出后另立为 Vormio/Vormio-Core#9。

**0.2.0（2026-10-15）**：先在分支 `r3-uri-keys` 上用 SDK 预发布版 0.0.9-rc.1 试用（OBJ 0.2.0-r3.1），Core 0.0.9 发布后换成 SDK 0.0.9：

- MTL 的材质 key 是 `material:<名称>`，按格式的查找规则给 MTLLoader 用的那一个：同名的材质以**最后一个**为准（与 Spine 图集以第一个为准相反，各按自己的运行时），之前的保留 `materials/<序号>`；名称为空或 key 超过 200 个字符时也保留 `materials/<序号>`。
- OBJ 只写了一个材质库（不同的文件名只有一个，同一个写几次也算一个）时，每个材质报告“材质定义”：从 `materials/<序号>` 指向材质库，`uriKey` 是 `material:<名称>`，证据是第一次 `usemtl` 的行。目标文件是 OBJ 写明的，所以这是写明的引用，材质库中没有这个材质时宿主显示缺失。
- 多个材质库时不报告 `uriKey`：材质在哪个材质库中，OBJ 没有写出，预览按后面的材质库为准。是否要表示“目标在几个文件之一中”，见 Vormio/Vormio-Core#9；它解决之前不报告。
- 测试：两个分析器之间的 key 一致（`table.obj` 的每个 `uriKey` 都是 `table.mtl` 报告中的 key）；同名材质、重复的 `mtllib`、空的与过长的材质名；两个材质库时没有 `uriKey`。包摘要与 Core 0.0.9 上的手工验收见 [Spine 设计计划](spine.md) §16。

## 8. 不在范围内

- 自由曲面与曲线（`curv`、`surf`、`parm` 等）、点与线元素（`p`、`l`）只计入诊断，不显示。
- PBR 扩展语句（`Pr`、`Pm`、`map_Pr` 等）：分析器照常报告贴图引用，查看器按 `MTLLoader` 能读的部分显示。
- DDS 等压缩纹理、绝对路径与 `http(s):` 地址（宿主不允许读取；分析器原样报告，宿主归为外部）。
- 动画与 OBJ 序列。

## 9. 测试与验收

- **Node 测试**：OBJ 与 MTL 分析的各类别、引用、证据行号、选项跳过、诊断、上限；“不适用”的判断；每份报告用 SDK 的 `parseReport` 校验。
- **Chromium 测试**（替身宿主）：缩略图与查看器在有材质、缺材质库、缺贴图、TGA 贴图、多个材质库时的画面；编译器目标文件三个扩展点都回答“不适用”；查看器就绪不依赖动画帧。
- **测量**：生成一个约 100 MB 的 OBJ（只在测试中生成，不入库），记录缩略图与查看器的耗时，决定是否需要在 README 写明大小上限。
- **手工验收**：在当时最新的 Core 发布版本上：启用确认框列出的权限；网格中的缩略图；查看器；`.obj` 与 `.mtl` 的组成、引用、被引用；删除材质库后显示缺失引用；一个含 MSVC 编译产物的文件夹全部是“不适用”且只问一次；原文件不变。

**手工验收**（2026-10-15，Core 0.0.8）：脚本驱动（Playwright 的 Electron 驱动，临时用户数据目录，不连官方目录，不模拟配色），Core 0.0.8 是 tag `v0.0.8` 的干净导出（`pnpm install --frozen-lockfile` 与 `pnpm run build`，未打包启动）。三个插件是本分支 `pnpm run package spine gltf obj` 的包（Spine 0.9.0 `d0aaceae…`，glTF 0.4.0 `48851a97…`，OBJ 0.1.0 `06889bab…`），在插件窗口用“安装插件包…”安装并启用。新资源库关联 `fixtures/spine` 的 `basic`、`preview`，`fixtures/gltf` 的 `animated`、`variants`、`props` 与整个 `fixtures/obj` 的副本，共 74 个文件；全程原文件的内容与修改时间不变。

- 安装确认框列出“缩略图：obj（还可读取…：mtl、png、jpg、jpeg、tga、bmp）”“查看器：obj（…）”“组成分析：obj”“组成分析：mtl”。
- `basic/table.obj` 有缩略图；查看器“60 个三角形 · 2 个材质”，木纹贴图显示；“组成”页签列出 Top、Legs、legs-front、Wood、Metal；“引用”页签的 `table.mtl` 已解析，点击跳到 `table.mtl`，它的“引用”页签中 `textures/wood grain.png` 已解析，“被引用”页签列出 `table.obj`。
- `problems/missing-library.obj` 在网格中标出“缺失引用”，查看器列出“absent.mtl（文件不存在）”。
- `not-obj/` 的两个编译产物与普通文本：没有缩略图、没有“分析失败”或“缩略图生成失败”；查看模式显示宿主的“这种文件暂时没有内置预览。”，插件查看器没有出现。
- 深色主题下 `layout/model/crate.obj` 的查看器背景是深色，后一个材质库的绿色与带 `#`、`\` 的贴图都正确。
- **Core 0.0.9（2026-10-15，OBJ 0.2.0）**：与 Spine 0.10.0 一起验收，方式见 [Spine 设计计划](spine.md) §16：`table.obj` 的 `table.mtl › Wood` 与 `› Metal` 已解析，点击跳到 `table.mtl` 并标出材质，`table.mtl` 的“按子资源 · 2”；两个材质库的 `crate.obj` 没有材质定义的引用。
- 未验证：大量编译产物时“只问一次”的表现（宿主行为与 Spine 的 `json` 相同，见 Spine 设计计划 §13）；真实的外部 OBJ 模型。多个材质库的场景（§7）见 Vormio/Vormio-Core#9。

## 11. 材质在几个材质库之一中（0.3.0）

状态：**已实现，SDK 预发布版 0.0.10-rc.1 试用中**（2026-10-15）。Core 0.0.10 承接 Vormio/Vormio-Core#9（R3b），先为 #5 与 #9 发布了 SDK 预发布版 0.0.10-rc.1（npm 标签 `next`），插件线在分支 `r4-agreement-candidates` 上试用，与 Spine 的 R4 试用（[Spine 设计计划](spine.md) §17）同一次。契约（`apiVersion: 5`）：引用可以用 `uris` 给出 2–16 个不重复的候选地址，必须带 `uriKey`，与 `uri`、`key` 三者只给一个，可以是推断的；只有一个候选时仍用 `uri`。优先规则固定一种：插件把会被采用的文件排在最前。宿主在查询时按顺序逐个看候选，只连接同一插件同一构建的分析结果：候选不存在就跳过；分析结果中有这个 key 就解析到它并显示是哪个文件；完整的分析结果中没有就看下一个；其他情况（忽略、越界、尚未分析、过期、失败、部分完成且没有这个 key、另一个构建）整条引用为“未知”并注明是哪个候选，不越过它解析到后面的候选；全部看完仍没有时写明的引用为缺失（只算一条），推断的为未找到。反查只把引用列在实际解析到的那个文件下。语义以 SDK README 的 “References that look in one of several files” 为准。

**决定**：

| 编号 | 决定                                                                                                                                                     | 理由                                                                                                                                                      |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M1   | 写了几个材质库时，每个材质报告一条“材质定义”引用，`uris` 是全部材质库（不同的地址各一个），顺序与预览读取的顺序相反；一个材质库时与 0.2.0 相同，用 `uri` | 预览按 `mtllib` 出现的顺序各读一次材质库，同名的材质以后面的为准（§5），所以后写的要排在前面，宿主按顺序找到的第一个含有这个 key 的材质库正是预览用的那个 |
| M2   | 同一个材质库写了几次时按第一次出现的位置排序                                                                                                             | 与预览相同（`summarizeObj` 各读一次，按第一次出现的顺序）；严格的“最后一次 `mtllib` 为准”会让 `a b a` 以 a 为准，但预览不是这样，README 写明              |
| M3   | 写了超过 16 个材质库的 OBJ 不报告材质定义，记一条信息诊断                                                                                                | 只报告前 16 个会把只在后面的材质库中定义的材质显示为缺失，不如不报告；实际的 OBJ 很少写这么多材质库                                                       |
| M4   | 仍是写明的引用：所有材质库都没有这个材质时显示缺失                                                                                                       | 材质库都是 OBJ 写明的，与 0.2.0 一致；预览中这样的材质也显示为灰色并列在“材质库中没有定义”                                                                |
| M5   | 各个 `mtllib` 本身仍各报告一条“材质库”文件引用；版本 0.3.0（试用构建 0.3.0-r4.1），声明的格式不变                                                        | Core 在 #9 中要求；改的只是分析结果                                                                                                                       |

**测试**：`tests/analysis.test.ts` 用 `fixtures/obj/layout/`（两个材质库，`Body` 在两个库中都有，`Label` 只在后一个）核对：`Body` 与 `Label` 的引用都是 `uris: ['../materials/paint.mtl', 'base.mtl']`，每个 `uriKey` 都是两个材质库报告中的 key；`a b a` 的顺序；16 个候选的上限与 17 个时的诊断；每份报告都用 SDK 的 `parseReport` 校验。`tests/analyzer.spec.ts` 在 Chromium 中得到相同的报告。`pnpm run lint`、`pnpm run typecheck` 与 `pnpm test` 全部通过（2026-10-15）。

**rc.1 在 `fixtures/obj/layout/` 上的结果**（Node 中的分析器，与 Chromium 相同）：`model/crate.obj` 报告两条材质库引用（`base.mtl` 第 1 行，`../materials/paint.mtl` 第 2 行）、两条材质定义（`materials/0` → `uris: ['../materials/paint.mtl', 'base.mtl']` ▸ `material:Body`，第 4 行；`materials/1` → 同样的候选 ▸ `material:Label`，第 29 行）与两条内部的“使用材质”。按 Core 写明的判定，`Body` 与 `Label` 都应解析到 `../materials/paint.mtl`，`base.mtl` 中的 `Body` 不列出这个 OBJ；删去 `paint.mtl` 中的 `Body` 后应解析到 `base.mtl`。没有在宿主中核对：没有加载 `apiVersion: 5` 的 Core 发布版本。试用构建的包摘要见 Spine 设计计划 §17（OBJ 0.3.0-r4.1 `6483caf1…`）。

**对 #9 的评审**（2026-10-15，已回复到 Vormio/Vormio-Core#9）：

1. 字段形状与“优先的排在前面”满足 OBJ：插件自己知道预览的合并顺序，把后写的材质库排在前面即可（M1）；候选数上限 16 对 OBJ 足够，超过时按 M3 处理。
2. “候选不存在就跳过”与预览一致：读不到的材质库在预览中也被跳过，同名材质取其余材质库中靠后的。
3. 请 Core 确认：候选的地址只按原文判重（SDK 拒绝重复的字符串），`a.mtl` 与 `./a.mtl` 这样指向同一文件的两个地址会被当作两个候选，宿主看两次同一个文件，结果相同；插件按报告的地址判重，不另做规范化。
4. 请 Core 确认：候选“被忽略、越界或不是文件”时整条引用为未知（而不是跳过），所以写了关联文件夹以外的材质库（例如 `C:\shared\paint.mtl`）的 OBJ，它排在前面时后面的材质都连不上，显示未知并注明这个候选。插件线认为合理（使用者能看到原因），只是与“不存在就跳过”的差别要在检视栏里说清。
5. 开发目录与 #3 相同：改动任何文件之后要重新分析全部材质库，否则每条引用都是“另一个构建”的未知。
6. 检视栏中候选列表、跳转与被引用页签在 0.0.10 的界面部分；验收条件中“两个候选、上千个材质时与单一目标同一量级”的耗时由 Core 测。Core 0.0.10 发布后插件线在它上面手工验收 `fixtures/obj/layout/` 的四种情形（都有、删去 `paint.mtl` 的 `Body`、两个都删、一个库未分析或失败）。
