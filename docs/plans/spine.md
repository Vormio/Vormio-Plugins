**0.7.0（2026-10-15）**：加入 Spine 3.7 骨骼 JSON 的组成分析（D4）。比较同一批官方示例的 3.7 与 3.8 JSON 导出，并列出 spine-ts 3.7 的 `SkeletonJson` 读取的字段：分析器用到的部分只有两处不同。一是 3.7 的 `skins` 是以皮肤名为键的对象（3.8 起是数组），皮肤没有专属的骨骼与约束，证据指针写成 `/skins/<皮肤名>/<插槽>/<附件>`；二是路径约束的动画时间轴叫 `paths`（3.8 起是 `path`），漏掉不会报错，只会少报引用。其余（列表、七种附件、链接网格、`deform`、绘制顺序、事件音频）相同。每个版本的运行时只读取自己的皮肤写法，所以 `skins` 的写法与版本不符时分析失败并说明原因。公开的 JSON 格式说明只描述当前的格式，3.7 的两处来自官方导出；分析器仍是自己写的代码，测试用插件已经带着的 spine-ts 3.7 读取同一文件来核对（`tests/skeleton-37.test.ts`），自己生成的 3.7 素材 `legacy/druid.json` 与 20 个官方 3.7 示例骨骼都与运行时读到的相同，官方示例没有任何诊断。故意去掉 `paths` 的处理时，这个测试在素材与示例上都失败。3.6 及更早仍不分析：皮肤写法与 3.7 相同，但没有官方样本可以核对。声明的格式没有变化，使用者不用重新启用。还没有在 Vormio-Core 中手工验收。

实施时与草案的不同：

- 重复区域按整个图集判断，不只是同一页面：Spine 按名称在整个图集中查找区域。
- 无法识别的字段只对页面报告。区域中的其他字段是 Spine 的“名称/值”附加数据，不报告。
- 页面文件名中的 `%`、`?`、`#` 编码后报告：宿主把地址当作 URI，会解码百分号、丢弃 `?` 与 `#` 之后的部分。

## 1. 目标

路线图把“第二种格式”列为验证组成契约是否通用的下一步。glTF 只有“一个文件 → 它直接写出的外部文件”这一层引用；Spine 的导出物是一组靠约定和名称连在一起的文件：

```text
hero.json（或 hero.skel）  骨骼、插槽、皮肤、附件、动画
   │  按同名约定配对，文件里不写图集的名字
   ▼
hero.atlas                 页面与区域；附件按“区域名”找到区域
   │  页面行写出图片文件名
   ▼
hero.png、hero2.png        贴图页
```

这个插件有两个目的：

- 让使用者在 Vormio 中看懂 Spine 资产的组成：骨骼、皮肤、附件、动画，以及图集用到了哪些贴图页。
- 把现有契约表达不了的地方，整理成带真实场景的 Core 需求（§8）。插件内部不绕过这些边界。

插件 ID `vormio-plugins.spine`，目录 `plugins/spine/`，首个版本 0.1.0，显示名称“Spine 骨骼动画”（名称中使用商标的问题见 §10）。

## 3. 图集分析器（0.1.0 交付）

**格式**：libGDX 文本图集，Spine 3.x 与 4.x 的两种写法都支持：

- 4.x：区域使用 `bounds`、`offsets`，页面可以有 `pma`、`scale`。
- 3.x：区域使用 `xy`、`size`、`orig`、`offset`。文件开头可以有空行。

分析只需要页面名、区域名与 `index`，其他字段只检查格式，不解释。

**子资源**：

| 类别 | key                                                         | 名称                                     | 上级     |
| ---- | ----------------------------------------------------------- | ---------------------------------------- | -------- |
| 页面 | `pages/<序号>`                                              | 页面行写的图片文件名                     | —        |
| 区域 | `regions/<序号>`；0.10.0 起按名称 `region:<名称>`（§16 K1） | 区域名；`index` ≥ 0 时写成“名称（帧 N）” | 所在页面 |

**引用**：每个页面引用它的图片，`uri` 为页面行原文，角色“贴图页”，证据为“第 N 行”。由宿主相对图集文件解析；`../` 与子目录照常处理。

**诊断**：

- 同一页面中重复的“名称 + index”：警告，两项都保留，key 不同。
- 无法识别的字段：信息。
- 页面缺少 `size`：信息，只有渲染时才需要。
- 不是图集文本（例如第一个非空行后紧跟的不是“键: 值”）：分析失败，并给出行号。

**上限**：与 SDK 的 `reportLimits` 一致。子资源超出时先保留全部页面与页面引用，再按出现顺序保留区域，报告标为部分完成。名称按 UTF-8 截断，去掉控制字符。

**读取**：通过 SDK 读取整个文件，不读配套文件，所以不声明 `companionFormats`。

## 4. 骨骼 JSON 解析（0.1.0 完成代码与测试，0.4.0 声明）

识别条件：顶层是对象，有 `skeleton.spine` 版本字符串，并且有 `bones` 数组。不满足时返回“不是 Spine 骨骼文件”（`NotSpineError`）；0.4.0 起三个扩展点都把它映射为 `notApplicable()`（§13）。

**子资源**（key 用序号，名称取文件中的 `name`）：

| 类别                                  | 来源                                                                                        | 上级     |
| ------------------------------------- | ------------------------------------------------------------------------------------------- | -------- |
| 骨骼                                  | `bones`                                                                                     | 父骨骼   |
| 插槽                                  | `slots`                                                                                     | —        |
| IK 约束、变换约束、路径约束、物理约束 | `ik`、`transform`、`path`、`physics`（物理约束为 4.2）                                      | —        |
| 皮肤                                  | `skins`                                                                                     | —        |
| 附件                                  | `skins[].attachments.<插槽>.<附件>`，类别细分为区域、网格、链接网格、包围盒、路径、点、裁剪 | 所在皮肤 |
| 事件                                  | `events`                                                                                    | —        |
| 动画                                  | `animations`                                                                                | —        |

附件的名称写附件键。用来查找图集区域的名字（`path`，没有时就是附件名）与附件键不同时，写成“附件键（区域 xxx）”。4.1 起的序列附件写成“区域 xxx（N 帧）”。

**内部引用**（`key` 加 `from`）：

| 发起者 | 目标                                                     | 角色               |
| ------ | -------------------------------------------------------- | ------------------ |
| 插槽   | 所在骨骼                                                 | 所在骨骼           |
| 约束   | 骨骼与目标（骨骼或插槽）                                 | 约束骨骼、约束目标 |
| 皮肤   | 皮肤专属的骨骼与约束                                     | 皮肤包含           |
| 附件   | 所在插槽；链接网格的父网格；裁剪附件的结束插槽           | 对应的角色名       |
| 动画   | 时间轴涉及的骨骼、插槽、约束、事件；形变时间轴涉及的附件 | 动画目标           |

同一对象之间、同一角色的引用只报告一次。证据写 JSON 路径，例如 `/skins/0/attachments/head/head`。

**文件引用**：0.1.0 不报告。

- 图集配对见 D3；0.8.0 起同名图集作为推断的引用报告（§14）；0.10.0 起附件使用的区域也作为推断的引用报告（§16）。
- `skeleton.images`、`skeleton.audio` 是编辑器中的非必需路径，相对于什么位置还没有用真实导出确认（§10）。事件的 `audio` 只写进事件名称，不报告。

**诊断**：

- 指向不存在的骨骼、插槽、皮肤或附件：引用略去，记警告。
- 骨骼层级成环：断开一处，记警告。
- 版本高于 4.2：警告。
- 3.6 及更早，或 `skins` 的写法与版本不符（3.8 起是数组，3.7 是对象）：分析失败，并说明原因。

**上限**：超出时先保留骨骼、插槽、皮肤，再按附件、动画、约束、事件的顺序略去，报告标为部分完成。

## 9. 许可与依赖

- **Spine Runtimes**（仓库 `EsotericSoftware/spine-runtimes`，许可 2025-04-05 版）。协议有两段：
  - 第一段：持有 Spine Editor 许可证的人，按 Spine Editor 许可协议第 2 节集成运行时，使用者不需要自己的许可证。
  - 第二段：其他人也可以集成运行时，条件是产品的每个使用者都自己持有 Spine Editor 许可证；再分发时附上协议与版权声明。
  - 分发方不持有许可证（2026-10-14 的决定），所以按第二段分发。产品是整个插件包：只用图集与组成分析的人也是使用者。Esoteric 的 Nate 在 2022 年答复 Flame 引擎时建议把含运行时的部分做成可选组件，许可只作用于它；本插件起初按此拆成两个插件，后来合并（见本文开头）。
  - 本插件要做的：插件包附上每个运行时的协议原文 `licenses/SPINE-RUNTIMES-<版本>.txt`（构建时从各自的包或 `vendor/` 复制；3.8、4.0 与 4.1 带 2019 年版，条款相同）；manifest 的 `description` 第一句写明许可要求；插件 README 与骨骼查看器底部也写明。插件无法核实使用者是否持有许可证。
  - 第 2.1(a) 节（重要且主要的功能）与第 12(e) 节是第一段的条件，按第二段分发时不涉及。
- **图集与骨骼 JSON 的解析**：不使用运行时，依据 Esoteric Software 公开的格式说明与自己生成的素材。公开的说明只描述当前的格式；3.7 骨骼 JSON 的两处不同来自 Spine 官方的 3.7 导出，测试用 spine-ts 3.7 读取同一文件核对，分析器不含运行时的代码（0.7.0）。
- **依赖**：`@esotericsoftware/spine-webgl` 4.0.31、4.1.56、4.2.120 与 4.3.13（npm 别名 `spine-webgl-4.0` 至 `spine-webgl-4.3`，各带同版本的 spine-core）；3.8 不在 npm 上，用 Spine Runtimes 仓库 `3.8` 分支 `28727aff` 的 `spine-ts/build/spine-webgl.js`，放在 `vendor/spine-ts-3.8/` 并记录来源。版本、许可与用途见插件 README。
- **素材生成器**：`scripts/fixtures/spine-binary.ts` 按运行时的二进制读取器写出 `.skel` 素材，是运行时的派生代码，受同一协议约束；它不进入插件包。
- **共用代码**：报告的截断、UTF-8 计量与名称清理和 glTF 插件相同，按仓库目录规划移到 `shared/`，glTF 插件随之改用，行为不变。

## 10. 开放问题

1. **商标**：插件名称中使用 “Spine” 是否只是说明用途？需要你确认，必要时咨询法律意见。本计划只摘录条款，不构成法律判断。
2. **开发与测试是否也算“使用者”**：第二段要求产品的每个使用者都持有许可证，开发与测试时也在运行 spine-ts。Nate 在 Flame 的答复中没有这样要求，但没有明说。2026-10-14 决定不等答复，默认使用者自带许可证。
3. **官方目录**：已决定（2026-10-14），在 R4（#5）之前上架，0.4.0 随目录序号 2 发布。目录不另外展示许可：要求写在 manifest `description` 的第一句，插件窗口的目录卡片上可见；安装与启用的确认框仍然看不到，见问题 4。
4. **启用确认框**：已在 Core `0c7fee0` 上确认，安装与启用确认框只列出权限，不显示 `description`；安装时“同时启用”默认勾选。Core 0.0.6 的验收（§13）中也一样。所以许可要求现在只在插件窗口、README 与骨骼查看器中可见，要靠 R4（#5）放进启用路径。

5. **路径的基准**：`skeleton.images` 与 `skeleton.audio` 在真实导出中相对于什么位置？需要用一份真实导出确认，再决定是否报告为文件引用。
6. **4.2 之后的格式变化**：骨骼 JSON 的解析在 4.3 发布后重新核对（骨骼预览已经用 4.3 运行时）。已知的一处：spine-core 4.3 的 JSON 读取器从顶层的 `constraints` 列表读取各种约束（每项带 `type`），不再读 `ik`、`transform`、`path`、`physics`，所以 4.3 骨骼 JSON 的组成分析列不出约束。0.4.0 照常附“比 4.2 新”的警告；要用一份 4.3 的真实导出确认之后再改解析。2026-10-15 改为用插件已经带着的 spine-core 4.3 读取同一文件核对（与 3.7 的做法相同），不再等真实导出，见 §15。

**实施要点**：

- `src/preview/figure.ts` 按 4.3 的类型写成，4.2 只替换初始姿势、插槽复位、按名称换皮肤、建贴图与绘制这五处调用（`src/preview/runtime-4.2.ts`）。
- 贴图页用图片元素，不用 ImageBitmap：4.3 运行时通过 WebGL 的解包设置预乘非预乘的贴图页，而 WebGL 对 ImageBitmap 忽略这个设置。
- 缩略图：初始姿势、默认皮肤（没有可见附件时用第一个有的皮肤），按可见范围取景，两倍大小绘制后缩小。读不到的贴图页让缩略图失败。
- 查看器：打开时播放第一段动画，与 Spine 自己的播放器相同；读不到的贴图页用透明像素代替并说明原因。
- 文件名编码移到 `shared/uri.ts`：图集的页面地址与骨骼的同名图集、贴图页地址都要编码 `%`、`?`、`#`。

**验收**：Node 与 Chromium 测试见插件 README。0.3.0 的包（`apiVersion: 1`）没有在 Core 0.0.5 上手工验收；同样的骨骼预览代码随 0.4.0 在 Core 0.0.6 上验收（§13）：网格中 `.skel` 显示初始姿势，查看器播放动画、切换皮肤，底部有许可说明，没有同名图集时显示原因，原文件不变。验收中发现两个宿主的缩略图问题（§13），会让个别 `.skel` 显示别的骨骼的缩略图或“The plugin page closed”。真实导出（需要持有 Spine 的人提供）只在手工验收时临时使用，这次没有。

## 15. 4.3 骨骼 JSON 的约束（0.9.0 计划）

状态：**已实现**（2026-10-15，路线图“下一批”第 1 项），结论写进了[插件 README](../../plugins/spine/README.md)；已在 Core 0.0.8 上手工验收（见下）。

实施时与草案的不同：

- 4.3 改名的字段不只约束列表：变换约束的目标骨骼叫 `source`，路径约束的插槽叫 `slot`，链接网格的父网格叫 `source`（在别的插槽时用 `slot` 指明）；动画多了绘制顺序文件夹 `drawOrderFolder`，按读取器全部处理。
- 滑块约束的内部引用：驱动它的骨骼（“约束骨骼”，只在有 `bone` 时）与它播放的动画（新角色“滑块动画”）。
- 素材没有改 `preview/` 的人偶（它要与二进制骨骼画得相同），而是新增结构素材 `basic/paladin.json`；人偶 `preview/knight.json` 也用运行时核对。
- 未识别的约束类型记警告并跳过（运行时同样跳过）。

**问题**：spine-core 4.3.13 的 `SkeletonJson` 从顶层的 `constraints` 数组读取约束，每项用 `type` 区分 `ik`、`transform`、`path`、`physics` 与新的 `slider`（滑块约束），全部放进 `skeletonData.constraints`；顶层的 `ik`、`transform`、`path`、`physics` 不再读取。0.8.0 的分析器按 4.2 的写法读，所以 4.3 的骨骼 JSON 列不出任何约束，约束相关的内部引用也缺失，只附“比 4.2 新”的警告。皮肤中的约束列表（`skins[].ik` 等）与动画中按约束类型分组的时间轴（`ik`、`transform`、`path`、`physics`，4.3 加 `slider`）仍是原来的写法。

**决定**：

| 编号 | 决定                                                                                                                        | 理由                                                                                                      |
| ---- | --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |

## 18. 二进制骨骼的组成分析（0.12.0 计划）

状态：**草案，待确认**（2026-10-16）。这是路线图 2026-10-15 那一批的“待定”项，读取方式留到 0.9.0 之后再定。现在骨骼 JSON 的组成分析覆盖 3.7 至 4.3，二进制骨骼只有缩略图与查看器：`.skel` 没有组成，也就没有同名图集与附件使用的区域的推断引用，图集的“被引用”里看不到用二进制导出的骨骼，而二进制导出更小、加载更快，产品中常用。

**读取方式**：两种做法里选在分析器页面中加载运行时。

| 做法                                                       | 代价                                                                                                                                                                                                                                                                                           |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 自写跨版本的二进制解析                                     | 3.8、4.0、4.1、4.2、4.3 五种布局（素材脚本 `spine-binary.ts` 的 `Traits` 列出了它们的差异），每种按运行时的 `SkeletonBinary` 移植约 800 行（3.7 的读取器就是这样来的），都是 Spine Runtimes 的派生代码；运行时升级时要跟着改                                                                   |
| 在分析器页面中加载包内的运行时读取，再把读出的数据转成报告 | 运行时已经在包内并按版本分块（§12），3.7 的读取器已有（0.6.0）；分析器页面只在遇到 `.skel` 时加载对应的分块（3.7 与 3.8 是整段 classic 脚本），骨骼 JSON 与图集照旧不加载；转换器只写一份，按 4.3 的数据类定型，各版本数据类的差异放进各自的模块（与 `figure.ts` 的 `Differences` 一样的做法） |

**决定**（待确认）：

| 编号 | 决定                                                                                                                                                                                                                                                                                                                                                                | 理由                                                                                                                                                        |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1   | 用运行时读取（上表第二种）：4.0 至 4.3 用 spine-core 的 `SkeletonBinary`，3.8 用 spine-ts 3.8 的，3.7 用插件移植的读取器（`readSkeletonBinary37`），得到 `SkeletonData` 后由一个转换器写出报告                                                                                                                                                                      | 不再新增派生代码；读取与缩略图、查看器走同一条路径，读得出就画得出，运行时升级时一起升                                                                      |
| B2   | 扩展点：`skeleton` 分析器的 `formats` 从 `json` 改为 `json, skel`，仍不声明 `companionFormats`。读取用一个不需要图集的附件加载器替身：按名称与 `path` 建附件，给区域与网格附件一个 1 × 1 的占位区域（运行时读完附件就按区域更新顶点与 UV，4.1 起没有区域会抛 “Region not set.”），序列照常建，不查任何区域                                                          | 与缩略图、查看器的 `skeleton` 扩展点一致（J2）；分析只读骨骼文件本身，与骨骼 JSON 相同。读取更多格式会改变权限指纹，使用者要重新启用，README 与升级说明写明 |
| B3   | 报告形状与骨骼 JSON 的分析器相同：同样的类别与 key（`bones/<序号>` 等按运行时列表的顺序，附件按皮肤、插槽与附件键），同样的名称写法（“附件键（区域 xxx）”、序列的帧数、事件的音频），同样的内部引用角色；同名图集与附件使用的区域照 K2 至 K5 作为推断的引用，查找名取运行时附件的 `path`，序列的帧名按 `Sequence`。同一份导出的 `.json` 与 `.skel` 除证据外报告相同 | 使用者看到的组成不因导出格式而异；图集的“被引用”同样列出二进制骨骼；测试可以直接比较两份报告                                                                |
| B4   | 二进制没有 JSON 指针，引用不写 `evidence`；诊断里提到对象时写类别与名称                                                                                                                                                                                                                                                                                             | 运行时不给出字节位置；SDK 的 `evidence` 是可选的                                                                                                            |
| B5   | 运行时读不了的文件（截断、损坏、没有对应运行时的版本如 3.6 与 5.0）分析失败并说明原因，用缩略图的同一套说明；不做部分报告。文件头读不出版本的 `.skel` 也失败（“不是 Spine 二进制骨骼”），不回答“不适用”                                                                                                                                                             | `.skel` 只有 Spine 使用（0.3.0 的理由），没有“不是我的格式”的情形；运行时遇到读不懂的内容就抛错，没有可用的部分结果                                         |
| B6   | 运行时读得进来、而骨骼 JSON 的分析器会诊断的情形，转换器同样诊断：同名对象（按名称引用时只会找到第一个）、版本比 4.3 新（警告）。运行时自己跳过的内容按运行时的结果，不另记                                                                                                                                                                                         | 两种形式的报告与诊断一致；运行时读取时已经按序号解析了引用，不会有“引用的名称不存在”                                                                        |
| B7   | 动画到目标的引用从时间轴对象取：骨骼、插槽与各种约束时间轴的序号，附件时间轴的附件名，事件时间轴的事件，绘制顺序时间轴涉及的插槽，形变时间轴的附件；各版本时间轴的类名与字段差异放进各版本的模块                                                                                                                                                                    | §4 的“动画目标”规则在数据类上的对应                                                                                                                         |
| B8   | 上限与裁剪沿用 `withinLimits` 与 K5（区域引用最多占一半，超出时部分完成）                                                                                                                                                                                                                                                                                           | 与 JSON 相同                                                                                                                                                |
| B9   | 版本 0.12.0（`apiVersion: 5`），在 0.11.0 于 Core 0.0.10 上验收并合并之后实施                                                                                                                                                                                                                                                                                       | 不与试用构建混在一起                                                                                                                                        |
| B10  | 测试素材：`spine-binary.ts` 扩到写事件与每种约束各一个（按版本可用的：IK、变换、路径；4.2 起物理；4.3 滑块），让仓库内的对照覆盖约束与事件；网格、链接网格与其余时间轴靠本机的官方示例对照（见下）                                                                                                                                                                  | 这些写法的核对成本有限，派生代码已经存在；把网格顶点、权重与各种曲线的写法全部补齐不值得                                                                    |

**实施要点**：

- 新文件 `src/analysis/binary.ts`（转换器，按 spine-core 4.3 的数据类定型）与各版本的差异模块。读取器与 `preview/runtimes.ts` 共用分块：4.x 直接 `import * as spine from 'spine-webgl-4.x'`，与查看器是同一个分块；3.7、3.8 用 `loadClassicScript`。分析器页面不需要 WebGL：只建 `SkeletonBinary` 与替身加载器，不建 `SceneRenderer`。
- `src/analyzer.ts` 按扩展名分支：`skel` 读字节，用 `preview/version.ts` 的 `skeletonVersion` 取版本、`runtimeLine` 选运行时，读不到版本或没有运行时时抛 `SpineError`。
- 皮肤的附件在 `Skin.attachments[插槽序号][附件键]`；链接网格的父网格在 `MeshAttachment` 的父网格字段；3.7、3.8 的字段名按各自的数据类。
- `.skel` 的报告与同一导出的 `.json` 只差证据：测试把 `.json` 报告的 `evidence` 去掉后深比较两者。

**测试**：

- Node 测试 `tests/skeleton-binary.test.ts`：六个版本的素材人偶（`preview/*.json` 与 `*.skel`）的报告除证据外相同（运行时在 Node 中加载的做法沿用 `preview-fixtures.test.ts`）；截断、3.6 与 5.0 的文件头、不是骨骼的字节都失败并说明原因；每份报告通过 `parseReport`；B10 扩展后的素材覆盖约束与事件。
- 官方示例对照（只在本机运行）：`SPINE_37_EXAMPLES` 已有；新增 `SPINE_EXAMPLES` 指向 Spine Runtimes 仓库对应分支的 `examples/`（每个示例都有 `.skel` 与 `.json`）时，逐个示例比较两份报告，覆盖网格、链接网格、裁剪、各种约束与时间轴；示例不进仓库，[开发说明](../development.md)写明用法。
- Chromium 测试：分析器页面经替身宿主对 `.skel` 返回报告，与同一页面对 `.json` 的报告相同；同一页面先后分析 3.8 与 3.7 的 `.skel`（classic 脚本一次只加载一个）。
- 包测试：契约不变，`skeleton` 分析器声明 `json, skel`；分析器页面能加载六个运行时分块。

**手工验收**（Core 0.0.10）：启用确认框列出“组成分析：json、skel”（升级要重新启用）；`preview/hero.skel` 有组成且与 `hero.json` 相同，推断引用 `hero.atlas` 与区域已解析，点击跳到图集并定位区域，`hero.atlas` 的被引用列出 `hero.skel`；`orphan.skel` 的推断引用未找到，不算缺失；`truncated.skel`、`spine-3.6.skel` 与 `spine-5.0.skel` 分析失败并显示原因；原文件不变。记录 Core 版本与未覆盖的部分。
